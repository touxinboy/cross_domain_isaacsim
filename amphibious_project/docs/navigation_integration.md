## 输入与任务命令

`run_navigation_interface.py` 接收一份记录观测的 JSON。先验证格式，不调用模型、不启动机器人：

```bash
python3 scripts/run_navigation_interface.py --observation observations/frame.json --validate-only
```

Qwen 图片/文字接口可用后，去掉 `--validate-only` 可执行一次 MSGNav 决策，保存 `frame.decision.json`。当前选中的对象或图片可能没有已定位的可到达观察点，此时输出 `goal_resolved=false`，不猜坐标。

未来在装好作者专用环境、下载权重并安排好 GPU 后，可加 `--omninav-checkpoint 实际权重目录`，接着测试一次专用航点头。此命令仍是记录观测的接口检查，不会驱动 Isaac。独立推理与控制的新测试入口见 `run_navigation_closed_loop.py`；先验证 shadow 模式，再进行短程执行，传感器与物理循环尚需服务器实测。

输入字段包括：

| 字段 | 来源与含义 |
|---|---|
| `source` | 实际观测写 `perception`；单元测试写 `synthetic_fixture` |
| `instruction` | 例如“找到河中尖顶的红色导管架”；这里的 jacket 指钢管支撑结构 |
| `capture_time_s`、`anchor_pose_xyyaw` | 同一观测时刻的仿真时间、世界 XY、航向，单位秒/米/弧度 |
| `objects` | 已检测对象的 ID、类别、观测估计的三维位置；可选已知可达的 `approach_xy_m` |
| `snapshots`、`edges` | 已采集图像以及对象关系对应的图像 ID |
| `frontiers` | 从已观测可通行图生成的探索候选点及对应图片 |
| `egocentric_images` | 当前相机图片路径 |
| `pointgoal.history` | 四次真实历史图片、XY 和严格递增的采集时间 |
| `pointgoal.tri_view` | 当前左、前、右三个相机的图片路径 |

图片路径相对 JSON 所在文件夹。对象位置、前沿和目标候选不能从隐藏 USD 场景内容或预选最优过河路线中偷取。当前仍需实现机器人视角的 RGB/深度采集、检测定位、观测地图和前沿生成，才能提供这些数据。

## 坐标和时间

Isaac 世界 Z 向上，机器人 +X 前、+Y 左。OmniNav 位置输入为参考机体的“右、前”，按原代码除以 0.3。适配器使用采集时刻的固定参考位姿，不把历史预测重新绑定到更新后的位姿。

原演示用第一个航点的长度乘 0.3 得到移动距离，另一个角度预测头给出方向。适配器保留这两个原输出，不把返回的五点列表直接当成已经可靠可跟踪的物理轨迹。当前坐标适配采用平面航向近似，坡岸俯仰和浮动姿态的相机外参适配仍需验证。

物理控制桥默认航点有效期 2 秒、单步最长 1.5 米；缺失或过期时输出零执行器需求。这不意味着浮在水里的刚体会瞬时停止。

本次高层语义选择耗时约 3.32 秒。因此实时接入时应在语义目标选定后重新采集最新图像和位姿，供短程航点头使用；不能把同一张旧图的参考位姿一路复用到持续运行的物理控制中。当前记录观测 CLI 尚不实现这个实时协调过程。

## 已找到的现有实现问题

`check_navigation_sources.py` 可离线重现和导出 JSON 报告：

1. OmniNav 的原 `parse_response` 将 `not found` 也判作 `found`，实际执行该解析函数已复现。我们的适配器不使用它宣布任务成功。
2. 原 PointGoal 演示包含两处 `agent.set_state`，其中一处用于随机脱困。这种执行方式不检验履带牵引、浮力和水中推进，已从物理适配中排除。
3. MSGNav 的 `explore_utils.py` 存储 `use_prefiltering` 标志却未读取，KSS 仍执行预筛选。这是对所检查模块的静态发现，尚不是整篇算法的评测结论。

接口测试使用合成观测、脚本回复和 CPU 张量，不代表模型实际推理，更不代表过河成功率。下一轮真实试验应分别记录：API/格式失败、目标定位失败、航点不可通行、执行/切换失败，避免把所有失败归给一个模型。
